## ТЕМА 0.2: GIT — НЕ ПРОСТО КОММИТЫ, А КУЛЬТУРА

### 1. Введение: что такое Git и зачем он нужен

Git — это **распределённая система контроля версий** (DVCS). Она позволяет отслеживать изменения в файлах, работать в команде без страха что‑то сломать, и возвращаться к любой предыдущей версии кода.

**Ключевые понятия:**
- **Репозиторий** — хранилище твоего кода и всей истории изменений.
- **Коммит** — снимок состояния файлов на определённый момент времени.
- **Ветка** — независимая линия разработки, позволяющая вести параллельную работу.

В 2026 году Git — это стандарт де‑факто. Без него ты не сможешь работать ни в одной серьёзной компании.

**Источники:**
- [Официальная книга Pro Git](https://git-scm.com/book/ru/v2) — лучший источник, бесплатно.
- [Git How To — интерактивный учебник](https://githowto.com/ru)

### 2. Основные команды и их назначение

Ниже я перечисляю команды, которые ты обязан знать наизусть. Я объясняю их суть, но синтаксис ты ищешь сам в документации — это тренирует навык работы с первоисточниками.

- `git init` – создаёт новый локальный репозиторий в текущей папке.
- `git add <файл>` – добавляет изменения в индекс (staging area), готовя их к коммиту.
- `git commit -m "сообщение"` – создаёт коммит с добавленными изменениями.
- `git status` – показывает текущее состояние репозитория (изменённые, добавленные, неотслеживаемые файлы).
- `git log` – выводит историю коммитов.
- `git diff` – показывает разницу между текущим состоянием и последним коммитом.
- `git branch` – список веток, `git branch <имя>` – создаёт новую ветку.
- `git checkout <ветка>` – переключается на другую ветку.  
  *В современном Git рекомендуется использовать `git switch`, но `checkout` всё ещё распространён.*
- `git merge <ветка>` – вливает изменения из указанной ветки в текущую.
- `git rebase <ветка>` – переносит коммиты текущей ветки поверх другой ветки.  
  *Даёт более чистую историю, но требует осторожности при работе с общими ветками.*
- `git stash` – временно прячет незакоммиченные изменения, чтобы переключиться на другую ветку.
- `git cherry-pick <коммит>` – применяет конкретный коммит из другой ветки в текущую.
- `git remote add origin <url>` – привязывает локальный репозиторий к удалённому.
- `git push origin <ветка>` – отправляет коммиты в удалённый репозиторий.
- `git pull origin <ветка>` – забирает изменения из удалённого репозитория и сливает с текущей веткой (фактически `fetch + merge`).
- `git fetch origin` – забирает изменения из удалённого репозитория, но не сливает их.

### 3. Стратегии ветвления

В индустрии сложились несколько подходов к организации веток. Ты должен знать основные.

| Стратегия | Описание | Когда использовать |
|-----------|----------|-------------------|
| **Git Flow** | Разделение на `master` (продакшн), `develop` (разработка), `feature/*`, `release/*`, `hotfix/*`. Очень формальная, много веток. | Крупные проекты с долгими циклами релизов. |
| **GitHub Flow** | Одна основная ветка `main`. Все фичи делаются в отдельных ветках, после завершения создаётся Pull Request и сливается в `main`. | Проекты с непрерывной доставкой (CD). |
| **Trunk-based Development** | Все разработчики работают в одной ветке (`main` или `trunk`). Изменения вливаются часто (несколько раз в день). Используются фича-флаги. | Быстрые команды, CI/CD, высокое тестовое покрытие. |

В нашем треке мы будем использовать **GitHub Flow** — он простой и идеально подходит для учебных проектов.

### 4. Conventional Commits — почему это важно

**Conventional Commits** — это стандарт для написания сообщений коммитов. Он делает историю понятной и позволяет автоматизировать генерацию changelog'а.

**Формат:**
```
<тип>(<область>): <краткое описание>

[необязательное тело]
[необязательный footer]
```

**Типы (самые частые):**
- `feat` – новая функциональность
- `fix` – исправление бага
- `docs` – изменения в документации
- `style` – изменения, не влияющие на логику (пробелы, форматирование)
- `refactor` – рефакторинг
- `test` – добавление или исправление тестов
- `chore` – обновление зависимостей, настройка проекта

**Пример:**
```
feat(auth): добавлена страница логина

Добавлена форма с валидацией через Zod.
Реализована отправка запроса на /api/login.
```

**Зачем это нужно:**
- История становится читаемой.
- Можно автоматически генерировать список изменений для релиза.
- Легче находить коммиты, которые внесли баг (git bisect).

**Источник:** [Официальная спецификация Conventional Commits](https://www.conventionalcommits.org/ru/)

### 5. Работа с удалённым репозиторием и Pull Request

1. **Создаёшь репозиторий на GitHub** (или GitLab, Bitbucket).
2. **Клонируешь** его локально: `git clone <url>`.
3. **Создаёшь ветку** для фичи: `git checkout -b feature/название`.
4. **Пишешь код**, делаешь коммиты с осмысленными сообщениями.
5. **Пушишь ветку** в удалённый репозиторий: `git push origin feature/название`.
6. **Открываешь Pull Request** (через интерфейс GitHub) на вливание в `main`.
7. В описании PR указываешь, что сделано, ссылаешься на задачу (если есть).
8. **Проходишь код‑ревью** (я буду выступать в роли ревьюера).
9. После аппрува выполняешь **сквош** (опционально) и **вливаешь** через `merge` или `rebase`.

### 6. Разрешение конфликтов

Конфликт возникает, когда в одной и той же строке файла сделаны разные изменения в сливаемых ветках.

**Как действовать:**
1. Git помечает конфликтные участки в файлах.
2. Ты открываешь файл в редакторе и видишь что‑то вроде:
   ```
   <<<<<<< HEAD
   твой код
   =======
   код из другой ветки
   >>>>>>> branch-name
   ```
3. Ты вручную правишь код, оставляя нужный вариант.
4. Удаляешь маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
5. Сохраняешь файл, добавляешь его `git add` и делаешь коммит слияния.

**Совет:** Чтобы избежать конфликтов, чаще делай `git pull` из основной ветки и перебазируй свою ветку (`git rebase main`).
