
## ТЕМА 0.4: ЖЁСТКИЙ TSCONFIG.JSON — НАСТРОЙКА TYPESCRIPT НА МАКСИМУМ

### 1. Введение: зачем нам жёсткий конфиг?

TypeScript — это не просто «добавить типы». Это мощный инструмент статического анализа, который может предотвратить целые классы ошибок ещё до того, как ты запустишь код. Но по умолчанию TS довольно мягкий — многие проверки выключены.

Мы включаем **все возможные строгие флаги**, чтобы TS стал твоим защитником, а не просто «цветным текстом в редакторе». Да, сначала будет больно — TS будет ругаться на код, который раньше работал. Но это **боль во благо**.

**Источник:** [Официальная документация по compiler options](https://www.typescriptlang.org/tsconfig)

---

### 2. Подробный разбор каждого флага в нашем `tsconfig.json`

Я разделю флаги на группы, чтобы было понятнее.

---

#### Группа 1: Базовые настройки окружения

- **`"target": "ES2022"`** — в какой стандарт JavaScript компилировать. ES2022 — современный, включает все фичи, которые поддерживают современные браузеры.
- **`"module": "ESNext"`** — система модулей. ESNext — современные ES-модули (`import`/`export`), которые поддерживаются в Vite и браузерах.
- **`"moduleResolution": "bundler"`** — способ разрешения модулей, оптимизированный для сборщиков (Vite, Webpack). Он понимает `exports` в `package.json`.
- **`"lib": ["ES2022", "DOM", "DOM.Iterable"]`** — какие встроенные типы (API) доступны: современный JS + DOM + итераторы.
- **`"jsx": "react-jsx"`** — как компилировать JSX. `react-jsx` — это новый трансформатор, который не требует `import React from 'react'` в каждом файле (работает с React 17+).

---

#### Группа 2: Строгие проверки (ключевые)

- **`"strict": true`** — включает целый набор строгих правил. Мы его оставляем, но добавляем сверху ещё больше строгости.
- **`"noUncheckedIndexedAccess": true`** — при обращении по индексу (например, `arr[0]`) TypeScript теперь считает, что результат может быть `undefined`. Это заставляет тебя проверять наличие элемента, предотвращая баги с пустыми массивами.
- **`"noImplicitOverride": true`** — если ты переопределяешь метод родительского класса, надо явно написать `override`. Это предотвращает случайные переопределения, когда ты не уверен, существует ли метод в родителе.
- **`"noFallthroughCasesInSwitch": true`** — запрещает «проваливание» (fallthrough) в `switch` без `break` или `return`. Ловит логические ошибки.
- **`"exactOptionalPropertyTypes": true`** — опциональное поле (например, `{ name?: string }`) теперь не может принимать `undefined` — только `string` или отсутствие поля. Это важно, когда бэкенд присылает `null` — ты явно обрабатываешь это.
- **`"noPropertyAccessFromIndexSignature": true`** — если у объекта есть индексная сигнатура `[key: string]: any`, то обращение `obj.field` запрещено, нужно писать `obj['field']`. Это заставляет явно описывать все поля в интерфейсах, исключая «магические» поля.
- **`"noImplicitReturns": true`** — все пути в функции должны возвращать значение явно. Ловит случайные `undefined`.
- **`"allowUnusedLabels": false`**, **`"allowUnreachableCode": false`** — запрещает мусор в коде.
- **`"verbatimModuleSyntax": true`** — это про ESM-синтаксис. Он требует явного использования `import type` для импорта типов, а не значений. Раньше TS позволял `import { SomeType } from 'module'` даже для типов (это было разрешено). Этот флаг запрещает такое — ты обязан писать `import type { SomeType }` или `import { type SomeType }`. Это делает код чище и лучше для сборщиков, потому что они точно знают, что импортируется (значение или тип).

---

#### Группа 3: Сборка и производительность

- **`"skipLibCheck": false`** — проверяет типы даже в `node_modules`. Это может замедлить сборку, но иногда ловит несоответствия версий библиотек. Мы оставляем его включённым для максимальной строгости.
- **`"forceConsistentCasingInFileNames": true`** — требует, чтобы имена файлов совпадали с регистром (на macOS это не всегда так). Помогает избежать проблем на Linux-серверах.
- **`"resolveJsonModule": true`** — позволяет импортировать JSON-файлы как модули.
- **`"isolatedModules": true`** — гарантирует, что каждый файл может быть обработан отдельно (важно для Vite, который использует esbuild для транспиляции).
- **`"esModuleInterop": true`** — помогает совместимости с CommonJS-модулями.
- **`"moduleResolution": "bundler"`** — уже упоминал, но это важно для Vite.

---

### 3. Почему мы не используем `"skipLibCheck": true`?

Многие проекты включают `skipLibCheck: true` для ускорения сборки. Но это означает, что ошибки в типах библиотек (или несовместимость версий) могут остаться незамеченными. Мы жертвуем скоростью ради надёжности.
